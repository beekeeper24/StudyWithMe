# StudyWithMe Architecture Draft

## Goal

StudyWithMe is a study community backend. The product connects study recruitment, participation, board communication, comments, replies, mentions, private chat, study chat, and notifications.

The important portfolio point is not simple CRUD. The important point is event-driven communication: user actions create domain events, and notification policies decide who should receive notifications.

## MVP Stack

- Java 21
- Spring Boot 3.5.14
- Spring Security OAuth2 Client
- JWT authentication
- Spring Data JPA
- QueryDSL
- PostgreSQL
- Redis
- WebSocket/STOMP
- Flyway
- JUnit5, AssertJ, Testcontainers
- Docker Compose for local development

## API Convention

All REST APIs use the `/api/v1` prefix.

Examples:

- `GET /api/v1/auth/me`
- `POST /api/v1/studies`
- `GET /api/v1/studies/{studyId}`
- `POST /api/v1/posts`
- `GET /api/v1/notifications`
- `GET /api/v1/chat/rooms/{roomId}/messages`

## API Response Convention

Successful responses use a stable envelope.

```json
{
  "success": true,
  "data": {},
  "message": "요청이 성공했습니다."
}
```

Error responses also use a stable envelope.

```json
{
  "success": false,
  "error": {
    "code": "STUDY-001",
    "message": "스터디를 찾을 수 없습니다.",
    "detail": null
  },
  "timestamp": "2026-05-21T03:49:00",
  "path": "/api/v1/studies/1"
}
```

Error codes use the `DOMAIN-XXX` format. Global framework-level errors use `GLOBAL-XXX`; domain errors should use names such as `AUTH-001`, `MEMBER-001`, `STUDY-001`, `CHAT-001`, and `NOTIFICATION-001`.

## Core Domains

- `member`: users, roles, profile, account status
- `auth`: OAuth2 login, JWT issuing, security context
- `study`: study lifecycle and study membership
- `post`: free board posts
- `studyroom`: study-room/place information posts
- `comment`: comments and one-level replies
- `mention`: nickname mention parsing and mention records
- `notification`: notification policy, unread state, notification delivery
- `chat`: private chat, study chat, messages, room membership
- `admin`: admin operations
- `report`: reports and sanctions

4. Free-board CRUD.
5. Study-room information CRUD and filtering.
6. Comments and one-level replies.

8. Mention parsing and duplicate notification prevention.
9. Private chat REST MVP.
10. Study chat REST MVP.
11. WebSocket real-time chat and notifications.
12. Admin member/post/comment/notice features.
13. Reports and sanctions.

## Current Scaffold

The initial project uses a Gradle wrapper generated by Spring Initializr.

Gradle is configured with a Java 21 toolchain. This means Gradle can build with JDK 21 even if the shell's default `java` command points to another installed JDK, as long as JDK 21 is discoverable.

The first package boundary is intentionally simple:

- top-level domain packages mark business areas;
- `global` contains cross-cutting configuration, security, events, common types, and exception handling;
- deeper `controller`, `service`, `domain`, `repository`, and `dto` packages should be added inside a domain when that domain is implemented.

Tests use an H2 in-memory database for the first context-load baseline. PostgreSQL remains the real local and deployment database.
